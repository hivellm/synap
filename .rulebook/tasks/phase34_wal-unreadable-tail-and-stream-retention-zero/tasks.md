## 1. Implementation
- [x] 1.1 Refuse to start, leaving the file unchanged, when opening the WAL finds that it ends in a complete, checksum-valid record this release cannot decode (`TailKind::Unreadable`), with an error naming the WAL path, the byte offset and that a newer release may have written it — before: both WAL opens (`WriteAheadLog::open` in `recover_all`, `AsyncWAL::open` in `PersistenceLayer::new`) call `wal_frame::prepare` → `repair`, which truncated every `ScanEnd::TornTail` whatever its `kind` with only a warning; now `repair` returns the new `PersistenceError::WALUnreadableRecord { path, position, reason }` for a kind that is not `is_torn()` before touching the file, `refuses_startup` includes it, so `main.rs` exits with it (an unreadable record before or after other frames: see 1.5)
- [x] 1.2 Keep truncating the tails a crash leaves (`Incomplete`, `ChecksumMismatch`, `Blank`) and starting, and test every shape through recovery and the WAL open — `repair` still truncates those three kinds; `torn_tail_then_new_writes_survive_two_restarts` now also covers a checksum mismatch and zero fill (two restarts each), next to the four cut-short shapes
- [x] 1.3 Make `retention_secs: 0` mean no time-based retention for stream rooms wherever it is read, keeping the buffer caps and positive retention unchanged — `Room::compact` (synap-core `core/stream.rs`), the only reader of `retention_secs`, computed its cutoff as `now - 0` and dropped every event; it now returns early on 0. The caps (`max_buffer_size`, `max_unread_buffer_size`) are enforced by `publish` and `Room::restored`, not by compaction, so they are unchanged; the server builds its stream manager from `StreamConfig::default()` (3600 s), and no config file exposes stream retention. Partition topics use their own `RetentionPolicy` (with an explicit `Infinite`) and are untouched
- [x] 1.4 Keep a room's earliest offset and statistics consistent when compaction removes events, including when it removes every event — found while testing 1.3: compaction never updated `stats.min_offset`, and when it removed every event it left `min_offset` and `stats.message_count` stale, so the next publish could not be read at its offset (`consume` indexes by `offset - min_offset`); `retain` could also remove an event between two live ones when the wall clock stepped back, breaking that contiguity. Compaction now pops expired events from the oldest end only and sets `min_offset` (and the stats) to the first event left, or to the next offset when none is
- [x] 1.5 Never truncate a complete, checksum-valid record this release cannot decode, whatever frame comes before or after it — found in review: `scan` asked `find_valid_frame` whether anything valid followed the first invalid frame, and it counted only frames that decode (`Frame::Valid`, `decode_payload(..).is_ok()`), so a frame failing its checksum or zero fill followed by an unknown record scanned as `TornTail { kind: ChecksumMismatch | Blank }` and `repair` truncated the record with the damage (and `synap-migrate` reported it as torn and left it out). The search is now `find_intact_frame` (natural successor and byte search both accept `Frame::Valid` or `TailKind::Unreadable`: complete, checksum matching, payload of at least `MIN_PAYLOAD_LEN`), so that layout is `WALInteriorCorruption` naming both positions and nothing is modified; when the first invalid frame is itself `Unreadable` and intact frames follow, `scan` fails with `WALUnreadableRecord` (before: `WALInteriorCorruption` before a valid frame, `TornTail` → `WALUnreadableRecord` before another unknown record), whose message now says "holds" instead of "ends in". Crash shapes are unaffected: zero fill fails the `len >= 20` candidate filter and has no matching checksum, and a torn append is cut short or fails its checksum. `WALInteriorCorruption`'s message says "a complete frame with a matching checksum follows"
- [x] 1.6 Make the stream retention spec and docs say what compaction does when timestamps step back — found in review: the spec said compaction MUST remove every event older than `retention_secs`, but 1.4 removes only the oldest run (a prefix) so offsets stay contiguous, and an event stamped later than the ones after it holds them until it expires. Removing an expired event from the middle would break `consume`'s `offset - min_offset` indexing, and clamping timestamps would only rewrite user-visible event times without expiring anything sooner, so the behavior stays and the spec (`specs/streams/spec.md`: requirement reworded, "Old events expire" and "Clock stepped back" scenarios), `StreamConfig::retention_secs`, `Room::compact`, `docs/features/broker-retention-and-prefetch.md` and `docs/specs/PERSISTENCE.md` describe it; `test_retention_keeps_offsets_contiguous_when_timestamps_step_back` now also checks that both go once the front event is that old
